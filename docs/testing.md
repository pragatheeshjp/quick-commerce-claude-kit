# Testing

Two kinds of tests, in both apps:

| Kind | Command | Needs | Runs in CI |
|---|---|---|---|
| **Unit / component** (mocked, fast) | `npm test` | nothing | yes |
| **Unit + coverage report** | `npm run test:coverage` | nothing | **yes** (reported, not enforced) |
| **Live** (real Supabase project) | `npm run test:live` (backend only) | `backend/.env` + `SUPABASE_ANON_KEY` | **no** (writes real data) |

Run them from `backend/` or `frontend/`. Coverage prints a table and writes an HTML report to `coverage/`
(git-ignored).

## Coverage in CI
The **Backend** and **Frontend** jobs in `.github/workflows/ci.yml` run `npm run test:coverage` instead of
`npm test`. Each run:
- shows a coverage table (statements, branches, functions, lines, plus any files under 90% line coverage) on the
  workflow run's **Summary** page, generated by `.github/scripts/coverage-summary.mjs`;
- uploads the full HTML report as an artifact (`coverage-backend`, `coverage-frontend`, kept 14 days).

It is **report-only**: no minimum is enforced, so a harmless change cannot fail the build over a percentage.
Test failures still fail the job. If you later want a gate, add `coverage.thresholds` to the `vitest.config.mts`
files (for example 90% lines) and the same command will fail when it is not met.

## Backend (`backend/tests/`, Vitest + Supertest)
| File | What it pins down |
|---|---|
| `jwt.test.ts` | Real `jose` verification against a local key set: signature, issuer, audience, expiry, unknown `kid`, tampered payload, `alg: none`, HS256 algorithm confusion |
| `roles-and-me.test.ts` | Admin role lookup and `GET /me` (including generic 500s that leak nothing) |
| `repositories-*.test.ts` | Every repository against a fake Supabase client: the queries that are built (scoping by user, pagination, search filter) and the Postgres/RPC error codes mapped to API errors |
| `services.test.ts` | Business rules: public vs admin product shape, cart pricing in integer paise, stock limits, address cap/default, order transitions and optimistic updates |
| `validators.test.ts` | Every Zod schema: bounds, mass-assignment rejection, search allow-list (incl. Devanagari/Tamil), idempotency keys, status rules |
| `middleware.test.ts` | `requireAuth`/`requireAdmin` (fail closed), error handler (no internals leaked), `validate` |
| `env-and-app-config.test.ts` | Env validation (exits, never prints secrets), CORS allow-list and preflight, security headers, body limit, trust-proxy, rate limiting |
| `routes-success.test.ts`, `catalog/commerce/orders/admin-users/api.test.ts` | End-to-end HTTP behaviour through the real Express app with fake repositories |
| `tests/live/*` | The same flows against the real database: RLS isolation, atomic stock, checkout races, idempotency, admin management |

Helpers: `tests/helpers/supabase-fake.ts` provides `fakeQuery()` (a chainable, awaitable query-builder double that
records calls) so repositories can be tested without a database.

## Frontend (`frontend/tests/`, Vitest + Testing Library + jsdom)
Component tests exercise behaviour through roles and labels (what a user or screen reader sees), not
implementation details. Network and auth are mocked at the module boundary (`@/lib/api`, `use-api`,
`auth-provider`, `cart-provider`).

Covered: auth provider and forms, route guard and open-redirect protection, cart provider (owner tagging, busy
state, stale responses), checkout (server quote, idempotency-key reuse and rotation, coupon fallback), orders and
cancellation, address book/form, admin screens (orders board, products, categories, admins, role gate), header,
pagination, API client, error mapping, money/rupee parsing, and validation schemas.

## Conventions
- **Money is always integer paise.** Tests assert exact integers, including classic float traps (`"1.10"`,
  `"0.29"`).
- **Test the failure paths**: authorization, validation, 404/409, double submits, stale data.
- **Security-relevant behaviour gets its own test** (ownership scoping, role checks, no leaked internals).
- Prefer `getByRole`/`getByLabelText`. If an accessible name is wrong in a test, fix the markup: the tests
  caught several real screen-reader issues this way.
- Keep `tests/live/*` out of the default run; they create and delete their own users/products.

## Do tests actually fail when the code breaks?
Mutation spot-checks were run: production code was deliberately broken in security- and money-relevant places
(JWT issuer/audience checks, admin check, ownership scoping, stock limit, coupon error mapping, order transitions,
idempotency key reuse, paise formatting/parsing, bearer-token header, cart owner check, open-redirect guard, admin
gate, error leakage) and the suite failed every time. If you add a rule like these, break it once on purpose and
confirm a test notices.
